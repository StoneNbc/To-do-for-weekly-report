# 人机协作开发流程

生效日期：2026-09-09。适用于本项目；用户当次明确指令优先。入口规则见[AGENTS.md](../AGENTS.md)。目标是减少重复上下文、重复检查和日志读取，保留数据正确性与可核实的验收。

## 1. 提需求与确定范围

- 用户描述目标、预期行为和必须保留的约束；不必整理代码路径或技术方案。
- Agent 检查现场后用简短说明确定本次范围；常规实现选择自主完成，只询问影响产品行为的关键歧义。
- 小修复直接开发，不额外设设计审批环节。大功能先明确关键交互、数据兼容和验收条件；只有用户要求先设计时，才在设计交付处停下。

## 2. 设计到开发的交接

- 长设计讨论结束后，建议用户在同一项目新建开发任务，用下列提示接手；不要复制整段聊天。小任务和同一缺陷修复继续当前任务。
- Agent 将目标、范围、已确认决定与精确文档章节、当前验证状态、下一步写入 `PROJECT_STATE.md`，总量遵循入口限制；其他实现事实由代码提供。
- 如果用户要求当前任务继续开发，直接继续；不自行创建任务，不把新建任务当成前置条件。新任务不默认 fork 旧历史。
- 同一目录只保留一个正在写代码的任务；切换前由用户结束旧任务的写入。不同检出需明确同步，不能假设状态相通。

```text
按本项目协作流程开发：<功能目标>。读取 AGENTS.md、PROJECT_STATE.md，按索引定位已确认设计。你完成实现、必要测试代码和最小相关检查，最终全量验证与 GUI 验收由我执行。
```

## 3. Agent 实现与局部验证

- 用 `rg` 定位后读取相关片段；独立检索合并执行。仅在需要理解整体结构时读全文件，不重复读取上下文已有内容。
- 同步修改必要测试。TXT 解析、重复任务定位、归档恢复、IPC 和发送授权等行为变更保留有意义的回归覆盖；简单文案或样式不新增机械测试。
- 调试时只运行受影响测试；类型边界变化可运行类型检查。成功只保留摘要，失败读取相关错误，不反复轮询或展示完整成功日志。
- 检查失败时确认是实现错误还是已批准行为改变；不为通过检查削弱有效断言。
- 不默认执行最终全量四项检查、GUI 自动化、安装或打包。用户委托、或局部无法定位而确需扩大检查时，说明原因后执行必要范围。
- 只维护受影响文档章节，完成一个可验证阶段后集中更新状态；保留必要进度沟通，不输出工具流水账。

## 4. 交付给用户验证

Agent 每次交付包含：实现结果、已实际执行的检查、待验证项、可复制命令、3–5 条与本次改动相关的人工验收步骤。纯文档改动只报告文档检查，不要求用户跑应用。

代码交付时，用户在项目终端运行：

```bash
pnpm typecheck && pnpm lint && pnpm test && pnpm build
```

命令在首个失败处停止；修复后先重跑失败项和受影响项，再完成尚未执行的项目。同一代码状态已通过的检查无需重跑；变更使旧证据失效时重新验证相关项。GUI 按需使用 `pnpm dev`；涉及迁移、删除或改名时使用隔离数据，Agent 提供具体方法。

用户无需发送全部成功日志，按实际执行范围回复：

```text
四项检查：全部通过 / 失败于 <命令>
人工验收：已执行项目及结果 / 尚未执行
失败时：测试名或操作步骤、预期与实际、首段相关报错（必要时附截图）
```

## 5. 修复与验收关闭

- 用户反馈失败后，Agent 在当前任务定位并修复，运行最小相关检查，说明用户需要重跑哪些项目；不要求用户诊断代码。
- Agent 不在等待用户期间持续轮询；以“已实现，待用户验证”交付，收到反馈再继续。
- 所需检查与人工项目均有结果后，更新状态为验收完成，注明 Agent 实测或用户报告、日期及对应改动范围；工作区期间有新修改须核实证据适用性。
- 提交、推送、发布仍需用户明确要求；人工验证分工不代表跳过验收，也不代表自动授权发布。

## 6. 判断流程是否有效

后续复盘优先看是否重复读文件、重复全量检查、扩大无关文档，以及人工反馈是否导致多次返工。不承诺固定 token 节省比例；需要统计时区分缓存输入、未缓存输入和输出，不能仅用耗时判断。
