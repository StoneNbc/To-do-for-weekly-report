## 1. 策略目标

本策略用于将设置功能拆分为可验证、可回滚、低耦合的开发阶段，重点保障：

- 跨 Main、Preload、Renderer 的契约始终保持一致。
- 便利贴颜色和不透明度支持实时预览，但不会因滑块拖动高频写盘。
- 配置保存失败时，运行时状态和界面都回到最后一次成功保存的值。
- 设置修改能够同步到悬浮窗、设置窗口、托盘菜单和右键菜单。
- 旧版 `config.json` 无需手工迁移，未知字段继续保留。
- 不扩大 Renderer 文件权限，不引入网络能力，不影响业务 TXT 数据。

---

## 2. 总体开发原则

### 2.1 契约先行

先定义设置快照、更新补丁、IPC 通道和 Preload API，再开发 Main 与 Renderer。每个阶段都以类型检查通过为基本退出条件，避免各进程各自发明字段。

### 2.2 主进程作为配置权威来源

- Renderer 只持有用于展示的设置快照。
- 配置校验、持久化、窗口不透明度和安全目录操作均由 Main 负责。
- Renderer 不读取或写入 `config.json`。
- 所有窗口以 Main 最后一次成功持久化的配置为准。

### 2.3 预览与提交分离

外观设置需要两种不同操作：

- **预览**：只临时应用到悬浮便利贴，不写配置文件。
- **提交**：校验并持久化最终值，成功后广播新快照。

不透明度滑块拖动时走预览；释放滑块、键盘完成调整或颜色选择确认时走提交。这样既能实时反馈，又不会为每一个像素移动写盘。

### 2.4 小步垂直交付

每一阶段都应形成可测试的闭环，不在一个提交中同时大规模改造配置、窗口、样式和测试。推荐按“契约 → 配置 → 窗口 → 页面 → 同步与收尾”推进。

### 2.5 保持既有业务边界

- 不修改 Today/Week 解析器和业务 TXT 格式。
- 不改变归档时间和归档流程。
- 不修改周报导出模板。
- 不增加任意路径 IPC。
- 不更改生产环境本地网络封锁策略。

## 3. 关键技术决策

### 3.1 使用专用设置契约

不将完整 `AppConfig` 直接暴露给 Renderer。新增仅包含可展示字段的公共契约：

```typescript
interface SettingsSnapshot {
  noteColor: string;
  noteOpacity: number;
  alwaysOnTop: boolean;
  completedExpanded: boolean;
  dataDirectory: string;
}

interface SettingsPatch {
  noteColor?: string;
  noteOpacity?: number;
  alwaysOnTop?: boolean;
  completedExpanded?: boolean;
}

interface AppearancePreview {
  noteColor?: string;
  noteOpacity?: number;
}
```

原因：

- 避免把 `template_path`、内部窗口位置或未来敏感配置无意暴露给 Renderer。
- 允许设置页面只提交白名单字段。
- 便于对配置文件字段名与 UI 字段名分别演进。

### 3.2 新增设置 API，而不是扩展通用文件 API

建议 Preload 契约：

```typescript
interface ElectronAPI {
  settings: {
    get(): Promise<ApiResult<SettingsSnapshot>>;
    previewAppearance(input: AppearancePreview): Promise<ApiResult<void>>;
    update(input: SettingsPatch): Promise<ApiResult<SettingsSnapshot>>;
    resetAppearance(): Promise<ApiResult<SettingsSnapshot>>;
    openLogsFolder(): Promise<ApiResult<void>>;
    copyDataPath(): Promise<ApiResult<void>>;
  };
  window: {
    openSettings(): Promise<void>;
  };
  events: {
    onSettingsChanged(listener: (snapshot: SettingsSnapshot) => void): () => void;
  };
}
```

`openDataFolder()` 可继续沿用现有接口，或在保持兼容的前提下由设置域复用。第一版不为了命名统一而删除已有通道。

### 3.3 配置提交必须可等待、可失败、可回滚

现有 `ConfigService.update()` 适合窗口移动等高频状态：它先更新内存，再防抖写盘，调用方不能直接获知最终落盘是否成功。

设置功能应新增异步提交能力，例如：

```typescript
commit(patch: ConfigPatch): Promise<AppConfig>
```

其语义必须是：

1. 在统一写队列中读取当前最新配置。
2. 校验补丁并构造候选配置。
3. 原子写入候选配置。
4. 只有写入成功后才把候选配置发布为“最后成功配置”。
5. 写入失败时保留旧配置并向调用方抛出或返回失败。

窗口 bounds 的防抖更新和设置提交必须共用同一串行队列，避免较晚完成的旧写入覆盖新设置。

### 3.4 使用 SettingsService 编排运行时效果

建议新增 `SettingsService`，集中负责：

- 生成 `SettingsSnapshot`。
- 校验并提交设置补丁。
- 临时预览颜色和不透明度。
- 提交成功后应用运行时状态。
- 提交失败后重新应用最后成功的外观。
- 广播设置变化。

该服务依赖抽象的运行时目标，而不是直接创建窗口：

```typescript
interface SettingsRuntimeTarget {
  previewAppearance(input: AppearancePreview): void;
  applySettings(snapshot: SettingsSnapshot): void;
  broadcastSettingsChanged(snapshot: SettingsSnapshot): void;
}
```

`WindowManager` 实现这些运行时动作，减少 IPC Handler 和 `main/index.ts` 中的业务编排。

### 3.5 设置窗口采用现有单 Bundle 路由

沿用现有查询参数方案：

```text
index.html?view=note
index.html?view=weekly
index.html?view=settings
```

`AppRouter` 继续使用白名单分支，未知值回退到 note。设置窗口由 `WindowManager` 维护单例引用。

### 3.6 颜色使用设计令牌，不散落条件样式

当前便利贴组件使用固定的 `stone`、`amber` 和白色样式。为支持自定义颜色和深浅前景，建议只在悬浮便利贴范围内引入 CSS 变量：

```css
--note-bg
--note-fg
--note-muted
--note-surface
--note-border
--note-accent
--note-focus
```

新增纯函数根据背景色计算深色或浅色前景方案，并为预设色建立单元测试。周记页与设置页继续使用现有独立样式，不参与主题变量改造。

### 3.7 整窗不透明度由 Main 控制

- 使用 Electron 悬浮窗口的不透明度能力应用 `0.6`–`1`。
- 不通过 CSS 只调背景透明度，因为需求定义为背景、文字和控件整体变淡。
- 创建悬浮窗时立即应用已保存值，避免先显示 100% 再跳变。
- 设置窗口关闭且仍存在未提交预览时，恢复最后成功保存的不透明度和颜色。

### 3.8 诊断入口只使用内部已知路径

- 数据目录和日志目录由 Main 启动时解析。
- “打开日志文件夹”不接受 Renderer 传入路径。
- “复制数据目录路径”由 Main 直接把已知路径写入剪贴板，避免通用剪贴板写入接口。
- 底层失败统一转换为 `ApiResult`，技术细节写本地日志。

## 4. 依赖顺序

```text
设置契约与校验
    ↓
ConfigService 可等待提交
    ↓
SettingsService 与 IPC
    ↓
设置窗口 / WindowManager / 菜单
    ↓
SettingsPage 与便利贴主题
    ↓
多窗口同步、失败回滚、平台验收
```

任何阶段若上游契约未稳定，不应提前在 Renderer 中硬编码临时字段。

## 6. 推荐提交拆分

建议保持每个提交可审查、可单独回滚：

1. `docs: define settings requirements and development strategy`
2. `feat(settings): add shared settings contracts and appearance utilities`
3. `feat(settings): add transactional settings persistence and service`
4. `feat(settings): add settings window commands and safe diagnostics`
5. `feat(settings): build settings page and note appearance controls`
6. `feat(settings): synchronize persisted general preferences`
7. `test(settings): cover rollback and cross-window settings flows`
8. `docs: sync settings implementation status`

如果某一提交需要同时改 Main、Preload 与 Renderer 契约，应优先保证该提交结束时 `pnpm typecheck` 通过，不留下长期的半契约状态。

## 7. 风险与应对

| 风险                       | 影响                     | 应对策略                                  |
| -------------------------- | ------------------------ | ----------------------------------------- |
| 滑块事件高频写盘           | 配置 I/O 抖动、写入竞争  | 预览与提交分离，最终值进入串行提交        |
| 保存失败但窗口已变更       | UI 与磁盘不一致          | Main 保留最后成功快照，失败后统一重新应用 |
| bounds 防抖写入覆盖设置    | 新字段或最新值丢失       | 所有配置写入共用一个顺序化队列            |
| 旧异步响应覆盖新选择       | 设置界面回跳             | Renderer 使用请求序号，只接受最新结果     |
| 设置窗口关闭时遗留预览     | 未保存外观继续生效       | `closed` 时重新应用最后成功配置           |
| 深色自定义背景不可读       | 任务和控件难以操作       | 设计令牌 + 前景方案纯函数 + 组件测试      |
| Electron 不透明度平台差异  | macOS/Windows 视觉不一致 | 限制为 60%–100%，双平台手工测试           |
| 菜单状态过期               | 不同入口显示不一致       | Main 广播设置快照，菜单打开时读取当前值   |
| 暴露完整 AppConfig         | 内部路径或未来字段泄露   | 使用专用 `SettingsSnapshot`               |
| 诊断入口变成任意路径能力   | 本地安全边界扩大         | Main 仅操作启动时解析的固定目录           |
| 一次改造所有 Renderer 样式 | 回归范围过大             | 主题令牌只覆盖便利贴页面及其专用组件      |
