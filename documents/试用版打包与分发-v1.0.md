## 1. GitHub Actions 是什么

GitHub Actions 是 GitHub 提供的自动化执行环境。它按照仓库中的 `.github/workflows/build-installers.yml`，在临时的 Ubuntu、macOS 和 Windows 云端构建机上安装依赖、检查代码、运行测试并生成安装包。

构建发生在 GitHub 的服务器上，不依赖开发者电脑持续开机，也不会复用开发者电脑中的 Electron 下载缓存。每次任务结束后，临时构建机都会被销毁，指定的安装包会被上传到 Actions Artifacts 或 GitHub Release Assets。

当前工作流包含四个任务：

1. `Verify source`：在 Ubuntu 上安装锁定依赖，运行 TypeScript、ESLint 和全量测试。
2. `Build macOS universal`：在 macOS 上生成兼容 Intel 与 Apple Silicon 的 DMG 和 ZIP。
3. `Build Windows x64`：在 Windows 上生成 x64 NSIS EXE 安装程序。
4. `Publish GitHub Release`：下载前两个平台的构建产物，创建或更新对应版本的 Release Assets。

任何校验或平台打包任务失败，Release 发布任务都不会执行。

## 2. 安装包与校验文件

| Release Asset | 使用者 | 说明 |
| --- | --- | --- |
| macOS `.dmg` | Mac 用户 | 首选安装格式；打开镜像后将应用拖入“应用程序”文件夹 |
| macOS `.zip` | Mac 用户 | `.app` 的备用压缩分发格式，解压后可移动到“应用程序” |
| Windows `.exe` | Windows x64 用户 | NSIS 安装向导，双击后按提示安装 |
| `SHA256SUMS-macos.txt` | Mac 用户或维护者 | 记录 DMG 和 ZIP 的 SHA-256 指纹 |
| `SHA256SUMS-windows.txt` | Windows 用户或维护者 | 记录 EXE 的 SHA-256 指纹 |

SHA-256 文件不是安装程序。它用于确认下载文件没有损坏、被替换或被篡改。

GitHub Release 页面还会自动显示 `Source code (zip)` 和 `Source code (tar.gz)`。它们是源代码快照，不是桌面应用安装包，不应发送给普通试用用户。

## 3. 触发方式与保存位置

工作流支持两种常用触发方式：

- 在 GitHub 仓库的 **Actions → Build desktop installers → Run workflow** 手动触发，用于验证构建。通常只在 Actions 页面生成临时 Artifacts。
- 推送名称以 `v` 开头的 Git 标签，例如 `v0.1.2` 或 `v0.1.2-beta.1`，用于正式创建 Release 并上传 Assets。

验证通过后会并行生成两个 Actions Artifacts：

- `sticky-weekly-macos-universal`：兼容 Intel 与 Apple Silicon 的 DMG、ZIP 和 SHA-256 校验文件。
- `sticky-weekly-windows-x64`：Windows x64 NSIS 安装包和 SHA-256 校验文件。

在 `main` 上手动触发时，构建结束后可在该次工作流页面底部的 **Artifacts** 下载，Artifacts 保留 30 天。

推送 `v*` 标签时，工作流会自动创建对应的 GitHub Release，并把 DMG、ZIP、EXE 和 SHA-256 校验文件添加到 **Release Assets**。Release Assets 不受 30 天的 Actions Artifacts 保留期限制，会随 Release 保留，直到维护者主动删除。

## 4. 发布新版本

发布前先修改 `package.json`，确保应用版本号与准备创建的 Git 标签一致。例如发布 `v0.1.2`：

```json
"version": "0.1.2"
```

提交并推送通过验证的代码：

```bash
git add -- package.json
git commit -m "release: prepare v0.1.2"
git push origin main
```

创建并推送版本标签：

```bash
git tag -a v0.1.2 -m "v0.1.2"
git push origin v0.1.2
```

然后在仓库 **Actions** 页面查看 `Build desktop installers`。全部任务成功后，在 **Releases** 页面确认五类 Assets 均已上传。

仅更新代码或文档、但不准备发布新版本时，只提交并推送分支，不修改版本号，也不创建 `v*` 标签。这样不会触发新的 Release。

## 5. 本地构建命令

macOS 通用安装包：

```bash
pnpm install --frozen-lockfile
pnpm dist:mac
```

Windows x64 安装包应在 Windows 主机运行：

```powershell
pnpm install --frozen-lockfile
pnpm dist:win
```

产物统一位于 `release/`。该目录已被 Git 忽略。

## 6. 校验安装包

macOS：

```bash
cd ~/Downloads
shasum -a 256 -- ./*.dmg
shasum -a 256 -- ./*.zip
cat SHA256SUMS-macos.txt
```

将命令输出与 `SHA256SUMS-macos.txt` 中对应文件的值进行比较，必须完全一致。

Windows PowerShell：

```powershell
Get-FileHash .\Setup.0.1.1.exe -Algorithm SHA256
Get-Content .\SHA256SUMS-windows.txt
```

Windows 中哈希字母大小写不影响比较；十六进制字符内容必须一致。实际 EXE 文件名以对应 Release Assets 为准。

## 7. 分发说明

- 不要发送项目源码、macOS `.app` 给 Windows 用户或整个 `release/` 缓存目录。
- 正式分发时优先从 GitHub Releases 页面下载对应版本的 Assets，不需要先下载 Actions Artifacts 压缩包。
- Windows 用户下载 `.exe` 安装程序。
- macOS 用户优先使用 `.dmg`；`.zip` 作为备用分发格式。
- 将同目录的 `SHA256SUMS-*.txt` 一并发送，便于测试者校验文件完整性。
- `data/` 不会进入安装包；每位测试者首次启动后生成自己的本地数据。

## 8. 未签名安装包提示

当前没有 Windows Authenticode 证书，也没有 Apple Developer ID 签名与公证：

- Windows 可能显示 SmartScreen“未知发布者”。仅让确认文件来自项目维护者的测试者继续运行。
- macOS 可能被 Gatekeeper 阻止。仅用于小范围内部测试，正式分发前必须配置签名与公证。

不要在仓库中提交证书、私钥或证书密码。后续签名材料只能通过 GitHub Actions Secrets 注入。

## 9. 分发前检查

1. 修改 `package.json` 版本号，试用版建议使用 `0.1.0-beta.N`。
2. 在 Windows 10/11 与 macOS 上分别安装并启动。
3. 验证托盘、关闭隐藏、设置持久化、周报导出和远程模型凭据保存。
4. 验证升级安装不会覆盖 `%APPDATA%/sticky-weekly/data` 或 macOS `Application Support/sticky-weekly/data`。
5. 记录安装包 SHA-256，并只通过可信渠道发送。
