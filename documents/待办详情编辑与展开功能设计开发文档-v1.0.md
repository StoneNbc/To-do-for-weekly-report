## 1. 文档目的

本文档定义“待办详情编辑与展开”功能在现有项目中的产品行为、TXT 数据格式、领域模型、跨进程契约、解析与存储规则、归档生命周期、React 交互和测试验收标准。

本文档是现有任务功能的增量设计。未被本文档明确修改的行为，继续遵循项目现有 PRD、开发设计和交接文档。

本次功能必须继续满足以下项目级硬约束：

- `today.txt` 与 `weeks/*.txt` 是任务数据的唯一事实来源。
- 允许标题、详情和完成时间完全相同的重复任务。
- 禁止按正文查找、去重、编辑或删除任务。
- 任务继续使用 `revision + line` 进行会话定位。
- 不向 TXT 写入持久化任务 ID。
- 未知行必须原样保留，不能静默删除或吸收到任务详情中。
- 归档固定先写周文件，成功后再修改 `today.txt`。
- Renderer 不直接访问文件系统，只通过 ElectronAPI 调用 Main。

## 2. 背景与目标

当前新增待办只填写单行任务内容，适合快速记录：

```text
- [ ] 完成项目方案 @添加:2026-08-30
```

实际执行过程中，用户经常需要补充背景、注意事项、步骤或备注。若把这些内容都塞进标题，会降低便利贴列表的可读性；若把它们建模成子任务，又会引入独立完成状态、排序和统计等不必要复杂度。

本次功能目标：

1. 新增待办仍然只填写标题，保持快速记录体验。
2. 用户可双击任务标题进入编辑模式。
3. 编辑模式可同时修改标题和多行详情。
4. 默认列表只展示标题。
5. 只有存在有效详情时才展示展开控制。
6. 每条任务可以独立展开或收起，允许多条同时展开。
7. 详情随任务保存到 TXT，并在完成、归档、历史完成和重新打开时保持。
8. 展开状态只属于当前 UI 会话，不写入 TXT 或配置。
9. 旧 TXT 文件无需迁移即可继续使用。

## 3. 范围与非目标

### 3.1 本期范围

- 今日未完成任务的详情编辑、展示和 TXT 持久化。
- 今日已完成但尚未归档任务的详情编辑和展示。
- 历史模式中全局待办的详情编辑和展示。
- 历史完成记录的详情编辑、展示和周文件持久化。
- 任务在今日完成、历史日期完成、跨日归档和重新打开时携带详情。
- 外部编辑 TXT 后重新解析详情并刷新界面。
- Parser、Repository、Service、IPC、Preload、Renderer 和 Mock 的契约同步。

### 3.2 本期明确不做

- 新增任务时填写详情。
- 详情独立勾选或独立完成状态。
- 子任务、任务树或多层嵌套。
- 详情独立 ID、排序、拖拽、提醒、截止日期或优先级。
- Markdown、富文本、HTML 渲染或附件。
- 详情搜索、全文索引或数据库。
- 持久化每条任务的展开状态。
- 在周记页面展示详情。
- 将详情写入本地模板周报或发送给远程 LLM。

后续若要把详情用于周报或远程生成，必须单独评审展示效果、提示词结构和隐私发送范围。

## 4. 产品模型

### 4.1 Task

Task 仍然是真正参与完成、撤销、统计、排序和归档的对象。

现有代码中的 `content` 继续表示任务标题，不在本次改造中大范围重命名为 `title`，以降低共享契约和历史逻辑的迁移风险。

```typescript
interface TodayTaskView {
  locator: TaskLocator;
  content: string;
  details: string;
  completed: boolean;
  addedDate?: string;
  completedAt?: string;
}
```

### 4.2 Details

`details` 是 Task 的普通多行说明文本：

- 不拥有独立完成状态。
- 不参与任务数量统计。
- 不参与任务排序。
- 不拥有独立定位器或任务 ID。
- 不作为子任务写入周报。
- 可以包含普通文字、编号、项目符号、空行和段落。

例如：

```text
今天需要完成第一版。

需要检查：
1. 架构图
2. 技术路线
3. 测试结果
```

无详情统一表示为：

```typescript
details: '';
```

领域快照不使用 `details?: string`，避免 Renderer 和 Service 反复处理 `undefined`。旧文件解析后自然补为 `''`。

### 4.3 UI State

展开状态不是业务数据：

```typescript
type ExpandedTaskKeys = Set<string>;
```

会话键使用当前快照定位器：

```typescript
const taskKey = `${task.locator.revision}:${task.locator.line}`;
```

由于项目明确不引入持久化任务 ID，任何 authoritative snapshot 替换后，旧定位器都可能不再指向同一任务。因此本期采用安全策略：

- 页面首次载入时全部收起。
- 外部文件刷新、日期切换或 mutation 返回新快照后全部收起。
- 应用重启后全部收起。
- 不尝试按标题或详情猜测并恢复展开状态。

这会牺牲少量状态连续性，但不会把旧任务的展开状态错误应用到另一条重复任务。

## 5. 用户交互设计

### 5.1 新增任务

新增流程保持不变：

1. 用户在底部单行输入框输入标题。
2. 按 Enter 或点击添加。
3. 新任务的 `details` 初始化为 `''`。
4. 不在新增区增加 textarea、弹窗或额外步骤。

### 5.2 默认展示

无详情：

```text
☐ 完成项目方案
```

有详情且收起：

```text
☐ 完成项目方案                         ▾
```

有详情且展开：

```text
☐ 完成项目方案                         ▴
  今天需要完成第一版。

  需要检查：
  1. 架构图
  2. 测试结果
```

展开控制建议使用紧凑的 chevron 图标，避免在默认宽度 320 px 的便利贴中占用“展开/收起”文字宽度，但必须提供：

- `aria-label="展开任务详情：<标题>"` 或 `aria-label="收起任务详情：<标题>"`。
- `aria-expanded`。
- 可见的键盘焦点样式。
- 鼠标 tooltip。

### 5.3 展开与收起

- 只有 `details.trim().length > 0` 时展示展开按钮。
- 点击只改变 Renderer 本地状态，不调用 IPC，不修改 TXT。
- 允许多条任务同时展开。
- 点击展开按钮不能触发标题编辑。
- 双击详情区域不能触发标题编辑。
- 详情使用纯文本渲染和 `white-space: pre-wrap`，不使用 `dangerouslySetInnerHTML`。
- 超长单词或 URL 使用 `overflow-wrap: anywhere`，避免撑破窗口。

### 5.4 进入编辑

- 双击任务标题进入编辑。
- 键盘聚焦标题后按 F2 或 Enter 进入编辑。
- 双击事件只绑定标题区域，不绑定整条任务。
- 同一时间只允许编辑一条任务。
- 保存过程中禁用当前编辑器和相关任务操作。

### 5.5 编辑器

编辑器至少包含：

```text
标题
[完成项目方案                         ]

详细说明
[今天需要完成第一版。                 ]
[                                      ]
[需要检查：                            ]

[取消] [保存]
```

控件：

- 标题使用单行 `input`。
- 详情使用可纵向调整或自动增长的 `textarea`。
- 编辑器位于任务行内部，宽度跟随便利贴窗口。
- textarea 初始建议显示 4–6 行，并设置合理最大高度后内部滚动。

键盘行为：

- 标题输入框按 Enter 保存。
- textarea 中 Enter 插入换行。
- 编辑组内按 `Command/Ctrl + Enter` 保存。
- 按 Escape 取消并恢复进入编辑前的标题和详情。
- Tab 在标题、详情、取消和保存之间正常移动。
- 本期不通过编辑组整体 Blur 自动保存，避免多行内容因误点而提交；保存必须由保存按钮或明确快捷键触发。

### 5.6 保存结果

- 标题为空时拒绝保存并在标题附近提示。
- 标题和详情都未变化时直接退出编辑，不发送 IPC。
- 保存成功后采用 Main 返回的新快照，并退出编辑。
- 保存失败时保留草稿和编辑态，展示可理解的错误。
- `FILE_CHANGED` 时退出旧编辑态、载入最新快照并提示用户重新编辑，不能自动覆盖外部修改。
- 保存成功后任务默认收起。

### 5.7 删除详情

用户将详情清空或只保留空白后保存：

- `details` 规范化为 `''`。
- TXT 中删除该任务的全部详情行。
- 展开按钮消失。
- 任务仍然保留，不改变完成状态、添加日期或完成时间。

### 5.8 今日、完成区与历史模式

同一个 TaskItem 详情能力适用于：

- 今日未完成列表。
- 今日已完成列表。
- 历史模式中的全局待办列表。
- 历史模式中的已完成记录。

周记窗口本期仍只展示任务标题和完成时间，不展示详情。

## 6. TXT 数据格式

### 6.1 设计原则

详情格式必须同时满足：

- 人类可读、可直接手工编辑。
- 不改变现有任务根行格式。
- 可以无歧义地表示空行和任意编号文本。
- 不把已有未知行误识别为详情。
- 删除或修改详情时不影响任务附近的未知内容。
- Today 和 Week 文件使用相同的详情行语法。

因此不采用“任务后所有非任务行都属于详情”的宽松规则，也不采用仅凭三个空格判断详情的规则。

### 6.2 详情行语法

标准详情行以两个空格、竖线开头：

```text
  | 详情内容
```

语法定义：

```typescript
const DETAIL_LINE_RE = /^  \|(?: (.*))?$/;
```

解析规则：

- `  | 内容` 解析为 `内容`。
- `  |` 解析为空详情行，用于保留段落空行。
- `  |  具有前导空格` 去掉格式分隔用的第一个空格后，仍保留正文自己的前导空格。
- `  |foo` 不符合标准格式，作为 unknown 原样保留。
- 详情内容中的 `1.`、`- [ ]`、`#`、`@HH:mm` 都只作为普通文本。

序列化规则：

```typescript
const formatDetailLine = (line: string): string => (line.length === 0 ? '  |' : `  | ${line}`);
```

### 6.3 `today.txt` 示例

```text
# 2026-08-30
- [ ] 完成项目方案 @添加:2026-08-30
  | 今天需要完成第一版。
  |
  | 需要检查：
  | 1. 架构图
  | 2. 技术路线
- [x] 回复客户邮件 @添加:2026-08-29 @14:20
  | 确认客户已经收到最终附件。
- [ ] 整理周报 @添加:2026-08-30
```

解析结果中的任务数量为 3，而不是 8。

### 6.4 周文件示例

```text
# 第35周 (2026-08-24 ~ 2026-08-30)

## 周日 08-30
- 完成项目方案 @添加:2026-08-30 @16:20
  | 今天完成第一版。
  |
  | 需要检查：
  | 1. 架构图
  | 2. 技术路线
```

归档根行继续使用现有周文件格式，不添加 `[x]`。

### 6.5 详情归属规则

详情行只有在下列条件全部满足时才属于任务：

1. 上方最近的连续业务节点是合法任务根行或该任务的另一条详情行。
2. 中间没有空白原始行、未知行、标题行或另一条任务根行。
3. 详情行符合标准 `DETAIL_LINE_RE`。

显式空详情行必须写成 `  |`。普通空白行会结束当前任务块，继续按现有 blank 节点处理。

孤立详情行不展示为详情，应作为 unknown 原样保留，并产生 `ORPHAN_DETAIL` 或 `UNKNOWN_LINE` 解析警告。

### 6.6 任务块

一个任务块由一条任务根行和紧随其后的零到多条详情行组成：

```text
TaskBlock
├── TaskRoot
├── TaskDetailLine 0
├── TaskDetailLine 1
└── TaskDetailLine N
```

`TaskLocator.line` 永远指向 TaskRoot 的物理行号，不指向详情行。

### 6.7 旧文件兼容

现有文件：

```text
# 2026-08-30
- [ ] 旧任务 @添加:2026-08-29
- [x] 已完成旧任务 @14:20
备注：这一行必须保留
```

解析后：

- 两条任务的 `details` 都是 `''`。
- 备注继续是 unknown 节点。
- 不发生自动迁移或整文件重写。
- 无 mutation 的 parse → serialize 必须保持原文件字节内容，现有 BOM 容错规则除外。

## 7. 文本解析器设计

### 7.1 AST 扩展

Today 增加详情节点：

```typescript
export interface TodayTaskDetailNode {
  kind: 'taskDetail';
  raw: string;
  line: number;
  content: string;
}
```

Week 增加详情节点：

```typescript
export interface WeekTaskDetailNode {
  kind: 'taskDetail';
  raw: string;
  line: number;
  content: string;
}
```

详情节点不保存持久化 ID，也不需要独立 locator。其归属由节点连续性决定。

### 7.2 解析顺序

Today 每行按以下顺序判断：

1. 空行。
2. 日期头。
3. Today 任务根行。
4. 合法且紧邻当前任务块的详情行。
5. unknown。

Week 每行按以下顺序判断：

1. 空行。
2. 周头。
3. 日期头。
4. Week 任务根行。
5. 合法且紧邻当前任务块的详情行。
6. unknown。

遇到 blank、unknown、header 或新 task 后，之前的详情归属上下文立即结束。

### 7.3 聚合详情

Parser 保留逐行 AST；Repository 通过任务根节点位置收集连续详情节点：

```typescript
interface TaskBlockRange {
  start: number;
  endExclusive: number;
}

function getTaskBlockRange(nodes: TodayNode[] | WeekNode[], rootIndex: number): TaskBlockRange;
function readTaskDetails(nodes: TodayNode[] | WeekNode[], rootIndex: number): string;
```

`readTaskDetails` 按详情节点顺序用 `\n` 连接，包含显式空详情行。

### 7.4 保真规则

- 未修改任务块的根行和详情行全部输出原始 `raw`。
- 修改标题但未修改详情时，详情行保持原始 `raw`。
- 修改详情时只替换该任务块中的详情节点。
- unknown、blank 和其他任务块的位置和原始文本保持不变。
- 重新索引时更新所有节点物理行号，但不生成持久化 ID。

## 8. Repository 设计

### 8.1 输入模型

```typescript
export interface TodayTaskChanges {
  content?: string;
  details?: string;
  completed?: boolean;
  completedAt?: string | null;
}

export interface HistoricalTaskInput {
  content: string;
  details: string;
  addedDate?: string;
  completedAt?: string;
}
```

### 8.2 新增任务

- 新增 API 仍只接收标题。
- 新任务详情为 `''`，不写详情行。
- 插入位置必须在最后一个已识别任务块之后，不能插到最后一条任务根行与其详情之间。

### 8.3 编辑任务

1. 校验 locator revision 和根行类型。
2. 标题有变化时只重写根行，并保留完成状态、添加日期和完成时间。
3. 详情有变化时找到目标任务块范围。
4. 删除目标块中已有详情节点。
5. 将规范化后的详情按行转换为标准详情节点并插在根行之后。
6. 重新索引并原子写入。

### 8.4 完成与撤销

- 只重写任务根行的 checkbox 和完成时间。
- 详情节点原样保留。
- 完成时间仍由 Main 的 Clock 生成。

### 8.5 删除任务

- 删除完整任务块，即任务根行和所有连续详情节点。
- 不删除块后面的 blank、unknown 或其他任务。
- 重复任务仍通过 locator 精确删除，不能使用标题或详情匹配。

### 8.6 Today 跨日处理

- 未完成任务顺延时保留完整任务块。
- 已完成任务清理时删除完整任务块。
- unknown 和非任务 blank 节点继续原样保留。

### 8.7 Week 插入、编辑与删除

- 插入历史任务时，将根行和详情作为一个块插入目标日期段。
- 已有日期段追加位置必须在该段最后一个任务块之后。
- 编辑历史任务时可同时修改标题、详情和可选完成时间。
- 删除历史任务时删除完整任务块。
- 判断日期段是否为空时，详情节点不单独计为任务；孤立详情 unknown 会阻止安全清理该日期段。

## 9. 校验与规范化

### 9.1 标题

沿用现有标题规则：

- 去除首尾空白。
- 不允许真实换行。
- 不能为空。
- 最大 2,000 个 Unicode 字符。

### 9.2 详情

新增独立规则：

- 输入类型必须为 string。
- 将 `\r\n` 和 `\r` 统一为内存中的 `\n`。
- 去除开头和结尾的纯空白行。
- 保留内部空行、空格、Tab 和换行。
- 只包含空白时规范化为 `''`。
- 拒绝 NUL 字符。
- 最大 20,000 个 Unicode 字符。

建议新增：

```typescript
export const MAX_TASK_DETAILS_LENGTH = 20_000;
export function normalizeTaskDetails(value: string): string;
export function assertValidTaskDetails(value: string): string;
```

IPC 使用独立 `detailsSchema`，不能复用当前禁止换行的 `contentSchema`。

## 10. 共享契约与 IPC

### 10.1 领域类型

以下类型增加必填 `details: string`：

- `TodayTaskView`
- `HistoricalTaskView`

`WeeklyTask` 本期不增加详情，确保周记、模板周报和远程 LLM 输入行为不变。

### 10.2 编辑输入

```typescript
export interface EditTodayInput {
  locator: TaskLocator;
  content: string;
  details: string;
  completedAt?: LocalTime;
}

export interface EditPendingFromHistoryInput extends HistoricalTaskLocatorInput {
  content: string;
  details: string;
}

export interface EditHistoricalInput extends AddHistoricalInput {
  locator: TaskLocator;
  details: string;
}
```

现有 add API 保持只接收 `content`；Main 为新增任务初始化空详情。

### 10.3 IPC 通道

不新增通道，继续使用：

## 11. Service 与完整数据生命周期

### 11.1 今日编辑

```text
Renderer 草稿
  → ElectronAPI.today.edit
  → IPC schema 校验
  → TaskService.editTodayTask
  → TodayRepository.updateTask
  → 原子写入 today.txt
  → 返回 authoritative TodaySnapshot
```

TaskService 继续在 mutation 前执行跨日补偿。

### 11.2 今日完成与跨日归档

任务完成时详情留在 `today.txt`。跨日归档时：

1. ArchiveService 从 TodaySnapshot 读取标题、详情、添加日期和完成时间。
2. 将完整字段写入 WeekRepository。
3. 周文件写入成功后，从 Today 删除完整任务块。
4. 未完成任务连同详情一起顺延。

`ArchivedTaskInput` 必须增加 `details: string`。

### 11.3 历史日期完成

从历史日期完成全局待办时：

1. 将标题、详情和添加日期写入所选日期的周文件。
2. 周写入成功后，从 `today.txt` 删除完整任务块。
3. 若 Today 删除失败，沿用现有回滚和部分失败语义。

### 11.4 重新打开历史完成任务

重新打开时：

1. 将历史任务的标题、详情和原添加日期写回 `today.txt`。
2. Today 写入成功后删除周文件中的完整任务块。
3. 周删除失败时回滚刚写入 Today 的完整任务块。

详情必须参与上述转移和回滚，不能只复制标题。

### 11.5 当前周聚合

周文件和 Today 中都可以保存详情，但 `WeeklySnapshot` 本期只投影：

```typescript
{
  (date, content, time);
}
```

因此：

- 周记 UI 不显示详情。
- 本地 TemplateAgent 不输出详情。
- 远程生成的已完成任务数据不包含详情。
- 远程生成的 pendingTasks 仍只使用标题。

这一投影只影响展示和报告，不影响 TXT 中详情的保存。

## 13. 文件监听与冲突处理

- Watcher 无需新增 scope，Today 和 Week 仍使用现有事件。
- 外部修改详情行会改变文件 revision，并触发现有刷新流程。
- 用户编辑期间收到外部刷新时，旧草稿不能自动写回。
- mutation 仍必须校验整文件 revision。
- 不能在 revision 冲突后根据标题、详情或二者组合寻找“看起来相同”的任务。
- Parser 发现孤立或非法详情行时记录行号和警告原因，但原文保持不变。

## 14. 错误与边界行为

| 场景                   | 预期行为                              |
| ---------------------- | ------------------------------------- |
| 标题为空               | 拒绝保存，保持编辑态                  |
| 详情为空或全空白       | 保存为 `''`，移除详情行               |
| 详情超过 20,000 字符   | IPC 返回 `INVALID_INPUT`              |
| 详情包含 CRLF          | 内存规范化为 LF，写回沿用文件整体 EOL |
| 详情包含 `1. xxx`      | 普通详情文本，不增加任务数量          |
| 详情包含 `- [ ] xxx`   | 普通详情文本，不解析为任务            |
| 详情包含 `@14:20`      | 普通详情文本，不解析为完成时间        |
| 孤立 `                 | ` 行                                  | unknown + warning，原样保留 |
| unknown 位于任务后     | 结束任务块，不吸收到详情              |
| 外部文件已变化         | `FILE_CHANGED`，刷新后由用户重试      |
| 删除有详情任务         | 删除根行及连续详情行                  |
| 归档周写失败           | Today 保持不变                        |
| 周写成功、Today 写失败 | 沿用现有部分失败错误和重复风险提示    |

## 16. 验收标准

1. 新增任务仍只填写标题，新增后没有详情和展开按钮。

## 20. 已知取舍与风险

### 20.1 无持久化任务 ID

展开状态会在快照更新后重置。这是为了避免按标题或内容猜测任务身份，符合项目现有 `revision + line` 设计。

### 20.2 详情格式是新增保留语法

用户手工写入以 `  |` 开头的行时，应用会将其解释为详情。必须在数据格式说明中记录这一点。孤立标记不会自动附着到其他任务。

### 20.3 归档仍是跨文件非事务

详情扩大了单条任务的数据块，但不改变现有先 Week、后 Today 的失败语义。极端部分失败仍可能产生重复归档，禁止通过标题或详情去重。

### 20.4 详情不进入周报

这能保持当前周记和报告输出稳定，并避免扩大远程发送范围；代价是详情只能在任务和历史记录界面查看。

### 20.5 多行内容增加 Parser 风险

所有写操作都必须以任务块为单位重新审查，特别是新增插入点、删除、跨日清理、历史段清理和失败回滚。只修改 UI 或 Today Parser 会形成数据丢失缺陷。
